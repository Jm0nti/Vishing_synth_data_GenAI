# Detecting Vishing While It Happens

**Behavioral biometrics for in-session risk detection in digital banking — a synthetic-data proof of concept.**

[Versión en español](README_es.md)

---

## What this project is

Vishing (voice phishing) is a fraud modality in which an attacker guides a banking
customer over the phone to execute a transaction on the attacker's behalf. The
customer operates voluntarily inside the legitimate mobile-banking application,
on their own device, with valid credentials. That single fact neutralizes the
defenses a bank normally relies on: channel validation, device fingerprinting and
credential checks all return *green*, because nothing about them is actually
wrong.

What is left as an observable is **how the session behaves**. Under an attacker's
instruction the customer types more slowly and in bursts, pauses before each
decision while listening, transcribes dictated data, corrects unfamiliar fields,
and confirms an operation that departs from their own habitual pattern.

This repository asks a single operational question:

> Is the behavioral trace a customer leaves *while the attack is in progress*
> enough to raise a risk alert **before the payment is authorized**, using only
> signals the banking application already observes — no call audio, no telephony
> metadata, no transcript?

Because labeled real vishing sessions are not available to us — confirmed labels
depend on customer claims, investigation outcomes and delayed reporting, and the
underlying behavioral telemetry is commercially and legally restricted — the
question is answered **inside a simulation we build and publish**. Everything
needed to reproduce it, contest it or recalibrate it is in this repository.

### What this repository contributes

1. **A dataset designed to imitate the mechanism of the fraud, not merely to be
   labeled.** 100,000 sessions over 38,000 clients, generated by a parameterized
   Gaussian-copula process, seeded and byte-reproducible, governed by an
   **explicit ceiling on univariate separability** so that simulation-induced
   separability is a declared parameter rather than an accident.
2. **Evidence that the behavioral signal is its own.** An ablation by feature
   family with bootstrap intervals, plus a call-proxy test and an independent
   permutation check, show the result does not reduce to knowing that a phone
   call is in progress.
3. **A measured ceiling on generative augmentation.** Because we control the true
   data-generating process, we can bound what *any* generator could contribute in
   this regime — +0.012 PR-AUC — which reframes a negative CTGAN result from
   "our GAN underperformed" to "the attainable prize is small, and here is its
   decomposition".
4. **An AutoML branch run on the same partitions**, not as a footnote.
5. **An evaluation protocol whose leakage properties are asserted in code**:
   partition first, feature contract computed inside training, balancing and
   augmentation as branches of the *training* set only, and a single opening of
   the test set.

## The dataset

`data/biocatch_sinthetic_data.csv` — **100,000 sessions × 58 columns, seed 42**.

| Attribute | Value |
|---|---|
| Sessions | 100,000 |
| Vishing sessions | 5,000 (5.00 %) |
| Clients | 38,000 (mean 2.63 sessions/client, median 2, p99 10, max 22) |
| Victim clients | 4,893 (max 2 vishing sessions per client) |
| Columns | 58 (44 of them enter the model) |
| Channel | 100 % mobile |
| Generator | `data/generar_dataset_sintetico.py` (numpy + pandas + scipy only) |

The dataset is **a designed artifact, not a convenience sample**. Its variables
are derived from two sources: the indicator catalogue that BioCatch describes
publicly for behavioral detection of social-engineering fraud (which indicators
exist and in which direction they move — not their parameters), and published
measurements of average human behavior on mobile devices. Each variable is given
a legitimate marginal and a vishing marginal; the assumptions behind each one,
and how firmly each is anchored, are documented in
[`data/notas_metodologicas_generacion.md`](data/notas_metodologicas_generacion.md).

### Generator architecture

1. **Client population with stable latent factors** (speed, steadiness,
   care/expertise), so the same client is recognizable across sessions. Intra-client
   correlation ρ = 0.55; roughly 55 % of behavioral variance is attributable to the
   client rather than the session.
2. **Gaussian copula.** Each variable is drawn as *z* ~ N(0,1) with a correlation
   structure (client factors + a per-session state factor) and then mapped to its
   target marginal through the quantile function. This preserves the requested
   marginal exactly while inducing realistic within-client and within-session
   correlation.
3. **Attack as interpolation, not substitution.** For a vishing session with
   activation *w* ∈ [0,1]:

   ```
   x = (1 − w) · F_legit⁻¹(u) + w · F_vishing⁻¹(u)      with the same u
   ```

   The victim keeps their relative rank — a fast typist stays relatively fast
   under coercion — and *w* controls how much the attack manifests. *w* derives
   from a per-session latent sophistication variable: **≈15 % of attacks
   (`P_ATAQUE_SOFISTICADO = 0.15`) barely activate the indicators and land inside
   the legitimate cloud**, creating an irreducible floor of false negatives that a
   fraud problem must have.
4. **Deliberate noise in the legitimate class.** ≈2.5 % of legitimate sessions
   receive the same overlay machinery at moderate intensity — a stressed user, an
   older adult, someone genuinely on the phone with a relative.

### The governing rule: an explicit separability ceiling

> **No feature may exceed a univariate AUC of `TECHO_AUC_UNIVARIADO` = 0.85
> against `is_vishing`.** When that rule collides with the distributions of the
> design brief, the rule wins.

This is the single most important design decision in the project. If one variable
explains the label, the dataset stops being evidence that the model learns a
multivariate pattern — and the whole experiment becomes an accounting exercise.
The ceiling makes simulation-induced separability a **declared quantity**.

Three explicit constants control separability, and are reported with every run:

| Constant | Value | Role |
|---|---|---|
| `TECHO_AUC_UNIVARIADO` | 0.85 | The ceiling itself |
| `ESCALA_GANANCIA` | 1.24 | Global multiplier on the per-variable gain table, clipped at 1.0 |
| `BETA_INTENSIDAD_BURDO` | (6.0, 1.7) | Attack intensity for unsophisticated attacks (mean ≈ 0.779) |
| `P_ATAQUE_SOFISTICADO` | 0.15 | Share of attacks that stay inside the legitimate cloud |

Measured result: **max univariate AUC = 0.8380** (`max_hesitation_duration_s`),
**0 features above the ceiling**, 4 above 0.80. The margin is a property of the
rule, not luck of the seed: across seeds 1, 7, 42 and 2026 the worst case is
0.8395.

Top of the univariate ranking, restricted to the 44 modeling features and measured
on the full dataset (the complete table, including the excluded columns, is in
[`data/reporte_validacion.md`](data/reporte_validacion.md)):

| 1 | `max_hesitation_duration_s` | 0.8380 |
| 2 | `data_familiarity_score` | 0.8330 |
| 3 | `segmented_typing_ratio` | 0.8129 |

### Two design notes that change how you read the data

**`phone_call_active` does not mean "there was a call".** It means *a call was
detected on the same device*. Taking the design brief's 85 % literally makes that
single variable reach AUC 0.90 and turns the dataset trivial. Reinterpreted, its
observed prevalence within vishing is 60.4 % and its univariate AUC is 0.7723 —
which is what makes the call-proxy test in R6 meaningful rather than circular.

**The `-1` sentinel is not a zero and not a missing value.** For
`transaction_amount_cop`, `time_to_transaction_s` and `days_to_claim`, `-1` means
"not applicable to this session". Any synthetic row — CTGAN in R2, SMOTE in R3 —
must restore it, or you end up with interpolated payment amounts in sessions
where no payment was attempted. `vc.repair_coherence` enforces this and
`vc.check_coherence` verifies it.

## Evaluation protocol

The protocol is the part of this project that makes the numbers worth reading.
Five properties, each asserted in code rather than described in prose:

1. **Partition first, transform later.** `R0` produces the canonical split before
   any balancing, augmentation or feature work touches the data.
2. **Grouped by client.** With 2.63 sessions per client and ~55 % of behavioral
   variance attributable to the client, a row-wise split puts the same person's
   sessions on both sides of the boundary and inflates performance. The split is
   `SPLIT_MODE = "grouped"`, by `customer_id`, stratified on whether the client
   had any vishing session, at 60/20/20.
3. **A row identity that survives everything.** `row_id` is a real column in the
   CSV and travels through every parquet, so `vc.assert_disjoint` can prove that
   no training row — original, CTGAN-generated or resampled — appears in
   validation or test.
4. **A feature contract computed only on training.** `vc.build_feature_contract`
   audits columns for constancy and exact duplication *inside train* and freezes
   the list. Ranking variables by discriminative power while looking at the test
   set is contamination, mild but real.
5. **One opening of the test set.** Model selection and threshold selection both
   happen on validation in `R4`. `R5` measures once. Going back and changing
   something after reading `R5` turns test into a second validation set.

Balancing and augmentation are **branches of the training set**, never of the
dataset. Every branch is re-checked against validation and test.

### The reference metric

At a base rate near 5 %, ROC-AUC is deceptively optimistic because it
under-penalizes false positives against an overwhelming majority class.
**PR-AUC** is the reference metric throughout. Alongside it we report two things
a bank actually has to plan around:

- **recall @ Precision = 0.90** — how much fraud you catch if you insist that 9
  out of 10 alerts be real.
- **Alerts per 100,000 sessions** — the queue an operations team has to staff.

Run order is **R0 → R1 → R2 → … → R8, no exceptions**. R0 creates the split that
everything else depends on, including R1's exploratory analysis, which is computed
on train only.

| Notebook | Where | Input | Output |
|---|---|---|---|
| `R0_contrato_y_split` | CPU | raw CSV | audit, feature contract, run manifest, split map, train/val/test |
| `R1_eda_train` | CPU | train | separability, odds ratios, correlations, profile, PCA, outliers, figures |
| `R2_ctgan_train_only` | **GPU** | train | 2 synthesizers, augmented train, KS report, detectability |
| `R3_balanceo_train` | CPU | train (± augmented) | 24 balanced training sets |
| `R4_entrenamiento_seleccion` | GPU/CPU | 26 training sets + validation | 260 models, validation leaderboard, winner |
| `R5_evaluacion_final` | CPU | winner + test | final test report with bootstrap CIs |
| `R6_ablation` | CPU | balanced train + validation | 6 ablation configurations with CIs |
| `R7_automl_comparable` | **GPU** | same splits | AutoGluon leaderboard |
| `R8_figuras_e_interpretabilidad` | CPU | winner + validation | figures, gain and permutation importance, SHAP |

### R0 — Data contract and canonical split

Validates the raw CSV against the expected schema (`DATASET_VERSION = "v3"`,
shape check) before anything else — it is cheaper to fail here than to discover in
R4 that the wrong file was uploaded. Then audits candidate columns for constancy
and exact duplication **on train**, builds the feature contract, creates the
client-grouped split, and writes a run manifest with the exact resolved package
versions.

The audit is expected to drop **nothing**, and that empty result is the
deliverable: it is the check that the uploaded CSV is the right one. If a constant
or an exact duplicate reappears, stop here.

The raw CSV is loaded with `vc.read_raw()`, not `vc.read_csv()`: `claim_category`
uses the empty string, which pandas would silently convert into ~95,000 false NaN.

### R1 — Exploratory analysis on train

Descriptive; feeds no downstream notebook, but produces every EDA figure and
table. Computed on train only, so nothing in the exploratory ranking is informed
by the test set.

Highlights from the current run:

- **Univariate AUC ceiling check**: max **0.8399** measured on train
  (`max_hesitation_duration_s`), 4 features above 0.80, none above the 0.85
  ceiling — consistent with the 0.8380 measured on the full dataset. R1 carries a
  `TECHO_AUC` constant that must match `TECHO_AUC_UNIVARIADO` in the generator —
  it is the only coupling between the generator and the pipeline.
- **Odds ratios** — with an explicit caution attached: `remote_access_tool_detected`
  has OR 37.67 and univariate AUC 0.5521. A high odds ratio on a very rare event
  is **not** predictive power.

  | Variable | OR |
  |---|---|
  | `remote_access_tool_detected` | 37.67 |
  | `phone_call_active` | 23.64 |
  | `suspicious_app_detected` | 12.94 |
  | `is_new_beneficiary` | 11.00 |

- **Transaction amounts**: median 1,662,824 COP in vishing vs. 249,229 COP in
  legitimate sessions (6.67×).
- **Tail enrichment**: `dead_time_periods` enriches the vishing rate 17.08× in its
  outlier tail.
- **PCA**: the first 5 components explain 33.0 % of variance — the signal is
  genuinely distributed, not concentrated in a couple of directions.

All figures are produced in **English** and R1 exposes configurable cells so plots
can be regenerated without editing code.

### R2 — CTGAN augmentation, fitted on train only

Two class-conditional `CTGANSynthesizer` models (SDV ≥ 1.5), fitted **only on
train**, generating 44 behavioral columns. Binary variables are declared
`categorical` so CTGAN uses the discrete conditional mechanism. Generated rows pass
through `vc.repair_coherence` — the same deterministic layer R3 uses — which
restores the `-1` sentinels and the logical consistencies the GAN does not learn.

The augmented dataset extends **train only**. Validation and test remain 100 %
original and are never touched.

The branch runs two quality tests: per-variable Kolmogorov–Smirnov, and an
**original-vs-synthetic classifier**. See [Results](#results) — this is a measured
negative result and it is reported as such.

Requires GPU (`ml.g4dn.xlarge` or better). Installs its own SDV/CTGAN pins in the
first cell.

### R3 — Balancing, on train only

Four resampling techniques × three target vishing rates (10 %, 20 %, 25 %), applied
**exclusively to train**, on each available source (`original`, and `augmented` if
R2 ran) — 24 balanced sets, plus the two unbalanced sources.

| Technique | Description |
|---|---|
| Random oversampling | Duplicates minority-class rows |
| SMOTE | k-NN interpolation of the minority class |
| Borderline SMOTE | SMOTE focused on decision-boundary examples |
| SMOTE + undersampling | Reduces the majority class ~10 % and applies SMOTE |

Every resulting set is submitted to the anti-leakage assertion against validation
and test. If R2 was not run, the `augmented` source is skipped with a warning
rather than failing mid-loop.

### R4 — Training and selection on validation

**260 models** = 2 data types × 13 training sets (12 balanced + 1 unbalanced) × 10
configurations (7 XGBoost variants + logistic regression + random forest + MLP).

| XGBoost variant | Configuration |
|---|---|
| `xgb_base` | depth 6, lr 0.1, 100 trees |
| `xgb_deep` | depth 9, lr 0.05, 300 trees, `min_child_weight=3` |
| `xgb_shallow` | depth 3, lr 0.1, 500 trees |
| `xgb_regularized` | depth 6, 200 trees, L1 1.0, L2 5.0, `min_child_weight=10`, γ 0.3 |
| `xgb_balanced` | `scale_pos_weight = n_neg/n_pos`, computed per dataset at fit time |
| `xgb_conservative` | subsample 0.7, colsample 0.7, γ 0.5 |
| `xgb_slow_learner` | lr 0.01, 500 trees, subsample 0.8 |

Both the decision threshold (F1-optimal on the PR curve) and the model choice are
made **on validation**. The test set is not opened in this notebook. XGBoost
resolves `cuda`/`cpu` at runtime via `vc.xgb_base_params()`, so the same notebook
runs on a GPU instance or a CPU one.

### R5 — Final evaluation

Executed **once**, at the end. The model and threshold are already fixed; nothing
is tuned here. Reports PR-AUC, ROC-AUC, recall, precision and F1 with **bootstrap
95 % confidence intervals**, plus recall@P=0.90, the operational load per 100,000
sessions, and the validation → test gap — which is the honest indicator of
selection overfitting.

### R6 — Ablation by feature family

Six configurations, all evaluated **on validation** (test was closed in R5),
replicating R4's winning configuration:

1. `context_transaction` — context and transaction only (11 features)
2. `behavioral` — behavioral biometrics only (33 features)
3. `behavioral_context`
4. `behavioral_transaction`
5. `all` — everything (44 features)
6. `all_sin_phone_call` — everything minus `phone_call_active` and `call_overlap_duration_s`

Configuration 6 is the **call-proxy test**: the direct answer to the objection
that a behavioral detector is really just a call detector.

### R7 — AutoML on exactly the same splits

AutoGluon `TabularPredictor`, `eval_metric='average_precision'`,
`presets='best_quality'`, `time_limit=5400` s, `use_bag_holdout=True`,
`num_bag_folds=8`, `num_stack_levels=1` — receiving **the same train, the same
validation and the same test** as the directed pipeline, measured with the same
metrics. Installs its own dependency tree in the first cell so it does not
contaminate the other notebooks.

### R8 — Figures and interpretability

Produces the figures no other notebook generates (KS distribution, PR-AUC by
algorithm and technique, variant × technique heatmap, feature importance) and adds
the interpretability layer: XGBoost cumulative **gain**, **permutation importance**
on validation, and optionally **SHAP** values.

The distinction matters for audit: cumulative gain is not additive and cannot
explain an individual case. Permutation importance and SHAP can.

## Results

### 1. In-session detection works, at a cost you can plan around

| Metric | Test |
|---|---|
| PR-AUC | **0.8458** [0.8266, 0.8652] |
| ROC-AUC | 0.9673 |
| Recall / Precision / F1 | 0.7903 / 0.8025 / 0.7963 |
| Confusion matrix | TN 19,008 · FP 193 · FN 208 · TP 784 |
| recall @ P = 0.90 | 0.6472 (threshold 0.9734) |
| Per 100k sessions | 4,838 alerts · 956 false · 1,030 missed |

The operating point that matters is the second one. At a precision of 90 % — nine
real cases per ten alerts — the detector still catches **65 % of attacks while the
session is open**. That is the number to argue with, not the PR-AUC.

**No selection overfitting.** The validation → test gap is **+0.0046**: test came
out *better* than validation. Choosing among 260 models bought nothing, and it did
not cost anything either.

**The leaderboard is flat.** 18 models sit within one point of the winner, and a
plain **logistic regression reaches 0.8350** — 1.5 points behind the best XGBoost.
The result is a property of the feature set, not of the algorithm. Any conclusion
that depends on the specific model choice would be fragile.

### 2. The behavioral signal is complementary, and it is not the call

Ablation, PR-AUC on validation:

| Configuration | Features | PR-AUC |
|---|---|---|
| `all` | 44 | 0.8504 |
| `behavioral_context` | 40 | 0.8435 |
| `all_sin_phone_call` | 42 | 0.8326 |
| `behavioral_transaction` | 37 | 0.8140 |
| **`behavioral`** | 33 | **0.8084** [0.7868, 0.8307] |
| **`context_transaction`** | 11 | **0.7834** [0.7622, 0.8054] |

Behavioral features **outperform** the contextual + transactional block by
**+0.0250**, with the point estimate above the rival's upper confidence bound, and
they **add materially on top of it**: `all` beats `context_transaction` by 0.0670.
The correct statement is complementarity — the behavioral trace carries
information that session context and payment attributes cannot supply.

**The call-proxy test.** Removing both call-related variables costs only
**−0.0178**. And the binary call indicator's **permutation importance is
−0.000044** — indistinguishable from zero. The model does not lean on knowing a
call is in progress; what signal there is lives in
`call_overlap_duration_s`, the continuous overlap duration, not in the binary flag.

This converts the most obvious objection to the whole premise into a measured,
dismissed risk.

**What the model actually uses.** 43 of 44 features are used (`is_atypical_hour`
never is), but 12 have permutation importance ≤ 0.0005: the model effectively
rests on about 32 variables.

### 3. Generative augmentation: a measured negative result with a measured ceiling

CTGAN passes a marginal-fidelity criterion and fails the one that matters:

| Test | Result |
|---|---|
| Mean per-variable KS | 0.0767 (11 of 44 above 0.10) |
| **Original-vs-synthetic detectability** | **AUC 0.8738 ± 0.0034** |
| Effect on PR-AUC | every balancing configuration **loses 2.1–3.1 points** |

A classifier separates real from generated rows at AUC 0.87. The marginals are
right and the joint structure is not — which is exactly the failure mode
per-variable KS cannot see. **KS does not validate a tabular generator.**

The instructive part is the causal thread between R2 and R8: the variable CTGAN
reproduces worst is `hour_of_day` (KS 0.2041, worst of 44), and `hour_of_day` is
the **third most determinant** feature by permutation importance (0.0254). The
generator's worst column is one of the model's most important ones.

**The oracle-generator experiment.** The natural response to "CTGAN lost" is "try
TabDDPM". `utils/_oraculo_aumento.py` shows that route has no headroom. It samples
new rows from the **true** generating process (other seeds of
`generar_dataset_sintetico.py`) — a perfect generator by construction:
detectability 0.5, exact marginals and joint structure, exact client–session
hierarchy. If even *that* barely helps, no learned generator can.

| Variant | Δ PR-AUC vs. baseline (0.8460) |
|---|---|
| Replica of R2's design (4× @ 1.5 %) | +0.0028 |
| **Same volume @ 5 % prevalence** | **+0.0120** ← the ceiling |
| Minority only, 2× positives | +0.0049 |
| Minority only, 5× positives | +0.0083 |
| Small mix (0.5× @ 5 %) | −0.0002 |
| **CTGAN (measured)** | **−0.036** |

The gap between CTGAN and perfection is 4.8 points, but **the total prize on the
table is 1.2**. Do not change generators expecting numbers.

Why the ceiling is low: there is no data scarcity. With ~60,000 training rows and
~3,000 positives the learning curve is already flat. Augmentation pays when you
have hundreds of positives, not thousands.

Two design details cost more than the choice of generator:

1. Targeting a 1.5 % vishing rate **dilutes** prevalence from 5.0 % to 1.88 %.
   With the same perfect generator that throws away **75 % of the available
   benefit** (+0.0028 vs. +0.0120).
2. Generating ~492,500 **legitimate** rows. The majority class does not need
   augmentation; minority-only reaches +0.005/+0.008 with 2 % of the compute.

And there is a structural mismatch: CTGAN is a model of independent rows, while
the data-generating process has ρ = 0.55 within clients over 2.63 sessions.
Assigning one synthetic client per synthetic row leaves ~89 % of the augmented
training set as singleton clients, evaluated against validation and test that have
2.63 sessions per client.

This is the finding that is hardest to obtain elsewhere: bounding what
augmentation *could* be worth requires knowing the true data-generating process,
which is the one thing a synthetic proof of concept actually has.

### 4. AutoML: reported as inconclusive, on purpose

| | Directed pipeline | AutoGluon |
|---|---|---|
| Test PR-AUC | 0.8458 | 0.8276 |
| recall @ P = 0.90 | 0.6472 | 0.6442 |
| Precision | 0.8025 | **0.8283** |

The AutoGluon branch (`WeightedEnsemble_L3`) lands 0.0182 PR-AUC behind — and
obtains the **better precision** of the two systems. We report this as
**inconclusive rather than a win**, because the comparison we ran was not
protocol-matched. AutoGluon carried three measured disadvantages:

1. It trained on the **augmented** training set while the directed pipeline used
   the original one. The measured penalty of augmentation (0.0227) is **larger
   than the observed deficit** (0.0182) — under equal conditions AutoGluon would
   likely win.
2. It fitted only 14 of 216 candidate models inside its time budget.
3. It ran without GPU or PyTorch, so its neural families never trained.

Claiming a win for directed design here would attribute to the approach what is
plausibly an artifact of the setup. A matched re-run — same original training set,
same budget, GPU available — is the honest way to settle it.

## What the evidence supports, and what it does not

**Supported.**

- A vishing attack in progress leaves a behavioral signature in the banking
  session strong enough to support a risk decision **while the session is still
  open**, using only signals the application itself observes.
- That signature is **not** a restatement of contextual and transactional
  circumstance: behavioral features beat the context+transaction block and add on
  top of it.
- The result **does not reduce to knowing a call is in progress**: removing both
  call variables costs 0.0178 PR-AUC, and the binary call flag has zero
  permutation importance.

**Refuted.**

- Class-conditional generative augmentation does **not** help in this regime — and
  the oracle experiment shows the ceiling for *any* generator is +0.012 PR-AUC.

**Inconclusive.**

- Whether directed design beats automated search. The comparison was not
  protocol-matched; see above.

**Boundary conditions that apply to all of it.**

- No labeled real vishing sessions were used. Every number was obtained on data we
  simulated ourselves, so the hypotheses are tested **within a regime whose
  parameters we declare**, not in production.
- Absolute metric values are internal to that regime. What transfers are the
  comparisons that hold the generator fixed, and the assumptions themselves.
- **No claim of production readiness is made.** Before any of this touches a real
  system, the assumptions in
  [`data/notas_metodologicas_generacion.md`](data/notas_metodologicas_generacion.md)
  — §8 lists what we would recalibrate first with real data — have to be
  re-estimated against real telemetry.

## How to run it

### 1. Environment

```bash
pip install -r requirements.txt
```

Version ranges follow the SageMaker Distribution 1.x / Python 3.11 compatibility
mask. The ranges are duplicated in `VERSIONES_ESPERADAS` inside
`vishing_common.py`; if you change one, change the other. Every notebook's boot
cell calls `vc.check_versions()` and warns if the kernel resolved something
outside the expected range.

Two heavyweight dependencies are **deliberately not installed here** — each
notebook that needs one installs it in its own first cell so it does not drag its
dependency tree into the others:

- `autogluon.tabular[all]>=1.0,<1.2` (R7)
- `shap>=0.44` (R8, optional)

### 2. Regenerate the dataset (optional)

```bash
python data/generar_dataset_sintetico.py --seed 42 --salida ./data
```

Requires only numpy, pandas and scipy — the generation is parametric on purpose,
so the data-generating process is fully under our control. It rewrites
`reporte_validacion.md` and `reporte_validacion.json` alongside the CSV.

**If you change the ceiling, change it in two places**: `TECHO_AUC_UNIVARIADO` in
the generator and `TECHO_AUC` in R1's configuration cell. That is the only
coupling between the two, and a mismatch either raises a false alarm or — worse —
silences a real one.

Before touching generator parameters, use the fast calibration bench rather than
running the whole pipeline:

```bash
python utils/_calibrar.py data/biocatch_sinthetic_data.csv
```

It measures, in ~8 seconds, the univariate ceiling and the multivariate PR-AUC of
the four key ablation configurations (`all`, `behavioral`, `context_transaction`,
`all_sin_phone`), replicating R0's grouped split. Always check several seeds:
separability margin should be a property of the rule, not of seed 42.

### 3. Local smoke test

Run the pipeline against the local filesystem before spending a GPU instance:

```bash
python utils/_smoke_local.py \
    --csv data/biocatch_sinthetic_data.csv \
    --out /tmp/smoke \
    --notebooks R0 R1 R3 R4 R5 R6 R8
```

R2 (CTGAN) and R7 (AutoGluon) are excluded: they need GPU and heavy packages.
Because R2 does not run, R3 produces only the `original` branch and R4 trains 130
models instead of 260. On CPU, R4 takes ~10 minutes. Harness dependencies:
`nbformat`, `pyarrow`, `imbalanced-learn`, `boto3`, `xgboost`.

### 4. Full run on SageMaker

Upload the canonical CSV to the single input path the pipeline expects, then run
the notebooks **in order**. The S3 layout is defined once, in
`vishing_common.Paths`:

```
s3://poc-vishing/v2/
├── 00_raw/            ← the only file you upload
├── 01_contract/       data_audit.csv · feature_contract.json · run_manifest.json
├── 02_splits/         split_map.parquet · train/val/test.parquet
├── 03_augmented/      synthesizers/ · train_augmented.parquet · quality/
├── 04_balanced/       {data_type}/{technique}/{ratio}.parquet
├── 05_models/         {data_type}/{variant}/{technique}/{ratio}.pkl
├── 06_results/        leaderboard · ablation · final_test · eda/ · automl/
└── 07_figures/
```

Change `BUCKET` and `PREFIX` in `vishing_common.py` to point somewhere else.


## Reproducibility

- **Seeds.** `vc.set_all_seeds()` runs in every boot cell and covers `random`,
  numpy and torch, including deterministic cuDNN. The generator is seeded at 42
  and byte-reproducible.
- **Versions.** `R0` writes the **exact resolved versions** to
  `01_contract/run_manifest.json`. That file, not `requirements.txt`, is the
  record of what a given run actually used.
- **Single source of truth for paths.** All S3 URIs come from
  `vishing_common.Paths`. Using `pd.read_csv` on an S3 path breaks the local smoke
  test — go through `vc.read_csv` / `vc.write_parquet`.
- **Device resolution.** XGBoost parameters come from `vc.xgb_base_params()`, which
  resolves `cuda`/`cpu` at runtime. Never hard-code `device="cuda"`: XGBoost ≥ 2.0
  fails on a CPU instance.
- **Known caveat.** In the reference run, `R7` and `R8` executed on a different
  interpreter than `R0`–`R6` (numpy 1.26.4 / scikit-learn 1.4.0 / xgboost 3.2.0
  versus 2.0.2 / 1.5.2 / 2.1.4). The exact-reproducibility claim covers `R0`–`R6`.

## A note on the source of the assumptions

BioCatch publishes general information about the behavioral vectors it uses to
detect banking fraud, but **does not disclose the exact variables nor how they are
computed**. What its public documentation supplies here is a *catalogue of
indicators and the direction in which each moves under social-engineering fraud* —
not parameters, distributions or thresholds. The numeric values in the generator
come from three clearly separated levels, marked as such in
`notas_metodologicas_generacion.md`:

1. **Anchored in cited literature** — e.g. `typing_speed_cps = 3.2`, from a
   large-scale published study of mobile typing speed.
2. **Orientative ranges from literature** — plausible bounds, not citable figures.
3. **Our own assumptions** — marked in the code with `SUPUESTO PROPIO`.

This separation is deliberate. It is what makes the simulation contestable: a
reader who disagrees with an assumption can find it, see which level it belongs
to, change it and re-run.
